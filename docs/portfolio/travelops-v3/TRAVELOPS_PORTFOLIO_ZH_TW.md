# TravelOps：從購票到營運追蹤

TravelOps 是獨立開發的旅遊電子票券履約與營運模擬系統。旅客、門市、場館和營運人員共用一套交易狀態，處理「款項已確認，票券卻還沒完成」這類跨步驟問題。所有場館、帳號與交易皆為合成資料；付款、供應商、退款和通知由本地 Mock 實作。

## 問題、解法與可觀察成果

線上與門市同時售票，不能各自扣除同一份庫存；付款通知可能重送，供應商也可能逾時。退款審核與場館核銷若各自更新狀態，還可能讓已退款的票券被使用。

系統將庫存與訂單狀態留在 MySQL，以列鎖協調通路；付款確認同時寫入開券 Outbox，交由 Redis Queue 和 Worker 處理。供應商回應遺失時，先查本地 Mock 帳冊，再決定是否重送。退款與核銷取得相同訂單鎖，營運端則比較內部交易和分開保存的 Mock 帳冊。

可觀察成果是完整的合成交易流程：購票後可以追蹤付款與開券、查看每個場館的剩餘權益；POS 預估兩張單館票為 NT$ 640，送出後由後端確認金額；對帳可顯示差異並留下處理原因。這些是系統行為的證據，沒有推算真實營收、節省比例或客戶成效。

## 四種角色如何使用

- **旅客**：瀏覽單館票與聯票，確認 14 天效期的起算方式、可售量與預估金額，建立訂單、模擬付款、追蹤開券及申請整筆退款。
- **門市**：在授權門市選商品、張數和現金／模擬卡片，核對即時摘要後提交；主管另可查看臺灣營業日日結。
- **場館**：使用指派場館的權限核銷個別權益，取得成功、重複核銷或暫停核銷等回饋。展示流程為輸入文字代碼，未驗證實機相機掃碼。
- **營運**：追蹤開券與投遞異常、審核退款、比較內外帳冊並記錄處理結果，依日期、通路、門市或供應商查看報表。

V3 保留 Blade、Livewire 和 Filament 的既有操作模式，補足旅客進度、退款暫停核銷提示、POS 送出前確認及營運差異比較。390 px 的手機版實際擷取自手機 viewport，並非縮小桌面畫面。

## 架構與技術

模組化單體以 PHP 8.4、Laravel 13.40.0、Livewire 4.4.8、Filament 5.11.2、Blade 及 Tailwind CSS 4 建立。MySQL 8.4/InnoDB 保存交易、庫存、票券、退款、Outbox、Webhook Inbox、稽核紀錄與獨立 Mock 帳冊；Redis 7.4 傳遞可重建的工作。Docker Compose 分開啟動 App、Worker、Scheduler、MySQL 及 Redis，GitHub Actions 執行品質與整合驗證。套件版本來自來源提交的 lockfiles；容器實際版本見本次媒體驗證報告。

系統總覽先解釋角色和資料路徑，再以交易流程圖展開鎖定與恢復邊界。沒有虛構雲端部署，也沒有實際第三方付款或供應商連線。

## 五項工程決策

1. **共用庫存列鎖**：線上與 POS 都使用同一套 Checkout，鎖住商品和庫存餘額後建立訂單快照及預留。以短交易換取一致的售票規則；未量測前不宣稱吞吐量。
2. **回呼冪等**：驗證簽章、付款參照、金額與幣別，用唯一事件與內容雜湊辨識重送及衝突。供應商及退款回呼另有時間窗驗證；不能把所有付款回呼都描述成具有同一時間窗。
3. **Transactional Outbox**：付款與開券工作一同提交到 MySQL。排程重新找出到期工作，Redis 承擔傳遞；穩定請求鍵、租約及先查再送處理回應遺失。供應商呼叫在訂單鎖外，結果再以新交易確認。POS 的本地 Mock 收款刻意留在外層交易，並不代表真實網路金流可照搬。
4. **退款與核銷互斥**：核准且尚未確認的退款暫停核銷。確認退款後才撤銷權益、回補售出庫存，並安排供應商撤銷；未確認的撤銷保留營運追蹤。只支援整筆退款。
5. **對帳與報表口徑**：原交易、外部 Mock 帳冊和人工處置分開保存。重跑對帳收斂差異，不把標記已處理當成改寫金額。畫面顯示新臺幣元，CSV 使用整數分；日期以臺灣營業日解讀。
